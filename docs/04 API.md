# Назначение

Данный документ определяет единые стандарты проектирования и разработки REST API проекта.

Все публичные HTTP-интерфейсы должны соответствовать правилам, описанным в данном документе.

Документ определяет:

- структуру API;
- правила именования;
- формат запросов и ответов;
- обработку ошибок;
- версионирование;
- аутентификацию;
- принципы безопасности.

---

# Архитектурный стиль

Проект использует **REST API**.

Каждый модуль предоставляет собственный набор HTTP-эндпоинтов.

Все запросы проходят через FastAPI.

API является единственной точкой входа для клиентских приложений.

---

# Версионирование

Все публичные маршруты должны содержать номер версии.

Пример:

```
/api/v1/
```

При несовместимых изменениях создаётся новая версия API.

Старые версии поддерживаются ограниченное время.

---

# Формат данных

API использует формат **JSON**.

Все запросы и ответы должны иметь корректный заголовок:

```
Content-Type: application/json
```

---

# Именование маршрутов

Используются существительные.

Правильно:

```
/users
/users/{id}
/subjects
/tasks
/topics
```

Неправильно:

```
/getUsers
/createUser
/deleteTask
```

---

# HTTP-методы

Используются стандартные методы HTTP.

| Метод | Назначение |
|--------|------------|
| GET | Получение данных |
| POST | Создание объекта |
| PUT | Полное обновление |
| PATCH | Частичное обновление |
| DELETE | Удаление объекта |

---

# Формат успешного ответа

Все успешные ответы имеют единую структуру.

```json
{
    "success": true,
    "data": {},
    "meta": {}
}
```

Поле `meta` используется для дополнительной информации (например, пагинации).

---

# Формат ошибки

Все ошибки имеют единый формат.

```json
{
    "success": false,
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "Validation failed",
        "details": {}
    }
}
```

---

# HTTP-коды

Используются стандартные коды состояния.

| Код | Назначение |
|------|------------|
| 200 | Успешный запрос |
| 201 | Объект создан |
| 204 | Нет содержимого |
| 400 | Некорректный запрос |
| 401 | Требуется авторизация |
| 403 | Недостаточно прав |
| 404 | Объект не найден |
| 409 | Конфликт данных |
| 422 | Ошибка валидации |
| 429 | Превышен лимит запросов |
| 500 | Внутренняя ошибка сервера |

---

# Аутентификация

API использует JWT.

После успешной авторизации клиент получает:

- Access Token;
- Refresh Token.

Access Token передаётся в каждом защищённом запросе.

Пример:

```
Authorization: Bearer <access_token>
```

Refresh Token используется только для получения нового Access Token.

---

# Авторизация

Доступ к ресурсам определяется ролями пользователя.

Основные роли:

- User;
- Admin.

Проверка прав доступа выполняется до выполнения бизнес-логики.

---

# Валидация

Все входящие данные проходят обязательную валидацию.

Для валидации используются схемы Pydantic.

Некорректные данные должны возвращать ошибку **422 Unprocessable Entity**.

---

# Пагинация

Все списки должны поддерживать пагинацию.

Стандартные параметры:

```
page
size
```

Ответ должен содержать информацию о пагинации.

Пример:

```json
{
    "success": true,
    "data": [],
    "meta": {
        "page": 1,
        "size": 20,
        "total": 152,
        "pages": 8
    }
}
```

---

# Фильтрация

Для получения выборок допускается использование query-параметров.

Пример:

```
GET /tasks?topic=functions&difficulty=easy
```

Фильтрация должна быть необязательной.

---

# Сортировка

Сортировка выполняется через query-параметры.

Пример:

```
GET /tasks?sort=created_at
```

Поддерживается направление сортировки.

Пример:

```
GET /tasks?sort=-created_at
```

Префикс `-` означает сортировку по убыванию.

---

# Поиск

Поиск выполняется через параметр:

```
search
```

Пример:

```
GET /topics?search=логарифмы
```

---

# Загрузка файлов

Файлы передаются через `multipart/form-data`.

После загрузки API возвращает информацию о сохранённом файле.

---

# Идентификаторы

Все ресурсы используют UUID.

Пример:

```
GET /users/{uuid}
```

Последовательные числовые идентификаторы в публичном API не используются.

---

# Ограничение запросов

Для защиты API применяется ограничение количества запросов (Rate Limiting).

Ограничения могут отличаться для различных категорий пользователей и отдельных маршрутов.

---

# Идемпотентность

Методы:

- GET;
- PUT;
- DELETE;

должны быть идемпотентными.

Повторный запрос не должен приводить к изменению результата.

---

# Документация API

API автоматически документируется средствами FastAPI.

Документация должна содержать:

- описание маршрутов;
- параметры;
- схемы запросов;
- схемы ответов;
- возможные ошибки.

---

# Логирование

Все запросы должны логироваться.

Минимальный набор информации:

- метод;
- маршрут;
- код ответа;
- время выполнения;
- идентификатор пользователя (если авторизован).

Конфиденциальные данные не должны попадать в логи.

---

# Безопасность

API должно обеспечивать защиту от:

- несанкционированного доступа;
- подделки JWT;
- передачи некорректных данных;
- чрезмерной нагрузки;
- раскрытия внутренней информации через сообщения об ошибках.

---

# Совместимость

При изменении API необходимо соблюдать обратную совместимость.

Ломающие изменения допускаются только при выпуске новой версии API.

---

# Definition of Done

API считается соответствующим стандартам проекта, если:

- используется REST;
- все маршруты имеют версию;
- соблюдается единый формат запросов и ответов;
- используется JWT-аутентификация;
- входные данные проходят валидацию;
- ошибки имеют единый формат;
- реализованы пагинация, фильтрация и сортировка;
- документация OpenAPI генерируется автоматически;
- соблюдаются требования безопасности и обратной совместимости.
