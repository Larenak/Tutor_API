# Назначение

Данный документ описывает принципы организации базы данных проекта, модель хранения информации, правила проектирования схемы и требования к работе с данными.

Документ определяет единые стандарты для всех модулей системы и является основным источником требований к проектированию сущностей и связей.

---

# Система управления базами данных

В качестве основной СУБД используется **PostgreSQL**.

Выбор обусловлен следующими преимуществами:

- высокая производительность;
- поддержка сложных запросов;
- надежность;
- транзакционность (ACID);
- расширяемость;
- широкая поддержка Python и SQLAlchemy.

---

# Общие принципы

При проектировании базы данных необходимо соблюдать следующие принципы:

- каждая таблица принадлежит одному модулю;
- модуль является владельцем своих данных;
- отсутствует дублирование данных без необходимости;
- используются нормализованные структуры;
- данные имеют явные связи;
- все изменения схемы выполняются через миграции.

---

# Владение данными

Каждый модуль является единственным владельцем своих таблиц.

Другие модули не должны изменять данные напрямую.

Доступ осуществляется через:

- публичные сервисы;
- доменные события.

# Связи между сущностями

Высокоуровневая схема связей выглядит следующим образом.

```text
User
│
├── EntryDiagnosticResult
├── Progress
├── Subscription
├── Analytics
├── Notification
├── AIConversation
└── Roadmap

Subject
│
└── Topic
     │
     ├── Theory
     └── Task
```

Каждая связь должна быть явно определена в модели данных.

# Идентификаторы

Во всех таблицах используются UUID.

Преимущества:

- глобальная уникальность;
- безопасность;
- отсутствие зависимости от последовательностей;
- удобство масштабирования.

Все идентификаторы являются неизменяемыми после создания записи.

---

# Временные поля

Каждая основная сущность должна содержать следующие поля:

- created_at
- updated_at

При необходимости дополнительно используются:

- deleted_at
- last_login_at
- completed_at
- expires_at

Все даты хранятся в UTC.

---

# Удаление данных

По умолчанию используется **Soft Delete** для пользовательских данных.

Физическое удаление допускается только если:

- данные являются временными;
- данные не имеют бизнес-ценности;
- это предусмотрено бизнес-логикой.

---

# Связи

При проектировании используются:

- One-to-One;
- One-to-Many;
- Many-to-One;
- Many-to-Many.

Связи должны быть минимально необходимыми и соответствовать предметной области.

---

# Ограничения целостности

Для обеспечения корректности данных используются:

- Primary Key;
- Foreign Key;
- Unique;
- Check Constraint;
- Not Null.

База данных должна гарантировать целостность независимо от логики приложения.

---

# Индексы

Индексы создаются для:

- первичных ключей;
- внешних ключей;
- часто используемых фильтров;
- поиска пользователей;
- поиска заданий;
- поиска тем;
- активных подписок.

Избыточное индексирование не допускается.

---

# Транзакции

Все изменения данных выполняются внутри транзакций.

Транзакции должны обеспечивать:

- атомарность;
- согласованность;
- изолированность;
- надежность.

---

# Миграции

Все изменения структуры базы данных выполняются через Alembic.

Запрещается:

- ручное изменение схемы;
- изменение структуры в production без миграции;
- несогласованные изменения моделей и миграций.

Каждая миграция должна быть:

- воспроизводимой;
- обратимой (если возможно);
- протестированной.

---

# Производительность

При проектировании необходимо учитывать:

- минимизацию количества запросов;
- использование индексов;
- предотвращение N+1 запросов;
- оптимизацию JOIN;
- ограничение объема загружаемых данных;
- использование пагинации.

---

# Кэширование

Redis используется для хранения данных, не требующих постоянного хранения.

Кэш не является источником истины.

Все критически важные данные должны храниться в PostgreSQL.

---

# Безопасность данных

Не допускается хранение:

- паролей в открытом виде;
- секретных ключей;
- токенов без защиты;
- конфиденциальных данных без необходимости.

Пароли должны храниться только в виде хеша.

---

# Резервное копирование

База данных должна поддерживать:

- регулярное резервное копирование;
- восстановление после сбоя;
- контроль целостности резервных копий.

---

# Правила проектирования моделей

Каждая модель должна:

- принадлежать одному модулю;
- иметь единственную ответственность;
- содержать только необходимые поля;
- иметь понятные имена полей;
- использовать UUID в качестве идентификатора;
- содержать временные поля;
- иметь корректные ограничения целостности.

---

# Definition of Done

Проектирование базы данных считается завершённым, если:

- все бизнес-сущности определены;
- каждая таблица принадлежит одному модулю;
- определены связи между сущностями;
- используются UUID;
- реализованы ограничения целостности;
- предусмотрены необходимые индексы;
- все изменения схемы выполняются через Alembic;
- структура базы данных соответствует архитектуре модульного монолита.
