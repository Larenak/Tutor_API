# Назначение

Данный документ описывает использование доменных событий (Domain Events) в системе.

События позволяют организовать взаимодействие между модулями без создания прямых зависимостей между ними.

Каждый модуль публикует события, описывающие произошедшие изменения, а заинтересованные модули могут подписываться на эти события и выполнять необходимую обработку.

---

# Что такое Domain Event

**Domain Event** — это сообщение о том, что в предметной области произошло некоторое значимое событие.

Событие описывает уже произошедший факт и не содержит бизнес-логики.

Примеры:

- пользователь зарегистрирован;
- задача решена;
- подписка активирована;
- дорожная карта построена.

---

# Цели использования событий

Доменные события используются для:

- уменьшения связанности между модулями;
- уведомления других модулей об изменениях;
- запуска фоновых процессов;
- синхронизации данных;
- повышения расширяемости системы.

---

# Общие принципы

При работе с событиями необходимо соблюдать следующие правила.

- событие описывает факт, который уже произошёл;
- событие публикуется только владельцем данных;
- событие не изменяет состояние системы самостоятельно;
- обработчики должны быть независимыми друг от друга;
- отсутствие обработчика не должно препятствовать публикации события;
- обработка события должна быть идемпотентной.

---

# Правила именования

Названия событий:

- используют прошедшее время;
- отражают завершённое действие;
- описывают бизнес-событие, а не техническую операцию.

Правильно:

```
UserRegistered
TaskSolved
RoadmapGenerated
SubscriptionActivated
```

Неправильно:

```
RegisterUser
UpdateTask
CreateRoadmap
```

---

# Структура события

Каждое событие должно содержать минимальный набор данных, необходимый для обработки.

Общая структура:

```json
{
    "event": "UserRegistered",
    "timestamp": "2026-07-10T12:00:00Z",
    "payload": {}
}
```

Событие не должно содержать избыточную информацию.

---

# Публикация событий

Модуль публикует событие после успешного завершения бизнес-операции.

Пример:

```
Создание пользователя

↓

Запись в БД

↓

Фиксация транзакции

↓

Публикация события UserRegistered
```

События не публикуются до успешного завершения основной операции.

---

# Подписка на события

Модуль может подписываться только на события, необходимые для выполнения собственной бизнес-логики.

Подписчик не должен изменять данные другого модуля напрямую.

Все изменения выполняются только через собственные сервисы.

# Обработка ошибок

Ошибка в обработчике события не должна нарушать выполнение основной бизнес-операции.

Каждый обработчик должен:

- логировать ошибки;
- корректно завершаться;
- поддерживать повторный запуск при необходимости.

---

# Логирование

Для каждого события рекомендуется логировать:

- имя события;
- время публикации;
- модуль-источник;
- модуль-получатель;
- результат обработки.

Это упрощает диагностику и анализ работы системы.

---

# Расширяемость

При добавлении нового модуля необходимо:

- определить публикуемые события;
- определить подписки;
- документировать изменения в данном документе;
- обеспечить совместимость с существующей системой событий.

---

# Ограничения

Доменные события:

- не заменяют прямые вызовы сервисов, если требуется немедленный результат;
- не используются для передачи больших объёмов данных;
- не должны содержать бизнес-логику;
- не должны создавать циклические зависимости между модулями.

---

# Definition of Done

Система событий считается корректно спроектированной, если:

- каждое событие отражает завершённый бизнес-факт;
- владельцем события является соответствующий модуль;
- события имеют единые правила именования;
- обработчики независимы друг от друга;
- отсутствуют циклические зависимости между модулями;
- события используются только для слабосвязанного взаимодействия между модулями;
- все публикуемые и принимаемые события задокументированы.
