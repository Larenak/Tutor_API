# Назначение

Модуль **Payments** отвечает за управление платёжной системой платформы.

Модуль обеспечивает монетизацию сервиса и управляет процессами оплаты, подписок и доступа пользователей к платным возможностям.

Модуль покрывает:

- создание платежей;
- обработку оплат;
- управление подписками;
- проверку статуса платежей;
- интеграцию с платёжными провайдерами;
- выдачу информации о платном доступе.

Payments существует для отделения финансовой логики от остальных модулей системы.

---

# Зона ответственности

Модуль отвечает за:

- создание платежных операций;
- обработку статусов платежей;
- интеграцию с внешними платёжными системами;
- управление тарифами;
- управление подписками;
- хранение истории платежей;
- проверку активного доступа пользователя;
- обработку платежных событий.

---

# Что НЕ входит в ответственность

Модуль не отвечает за:

- создание учебного контента;
- определение ценности подписки;
- управление пользователями;
- выдачу учебных материалов;
- управление прогрессом;
- генерацию AI-ответов;
- авторизацию пользователей.

Payments только определяет наличие оплаченного доступа.

---

# Ограничения

Модуль не должен:

- хранить данные банковских карт;
- самостоятельно проводить платежи;
- изменять данные других доменов;
- управлять правами доступа напрямую;
- хранить пользовательские профили;
- содержать логику обучения;
- создавать циклические зависимости.

# Архитектура

Payments является изолированным бизнес-модулем, который взаимодействует с внешними платёжными системами.

Основной поток:

```

User  
|  
v  
Frontend  
|  
v  
Payments Module  
|  
+--> Payment Provider  
|  
v  
Payment Status  
|  
+--> Subscription  
|  
v  
Access Control

```

Пример:

```

Пользователь выбирает тариф  
|  
v  
Payments создаёт Payment  
|  
v  
Платёжный сервис обрабатывает оплату  
|  
v  
Webhook подтверждает оплату  
|  
v  
Активируется подписка

```

# Компоненты

## Router

Назначение:

Предоставляет API для платежных операций.

Ответственность:

- создание платежа;
- получение истории;
- просмотр подписки;
- обработка webhook-запросов.

Не содержит:

- финансовую логику;
- работу с провайдерами напрямую.

# Бизнес-правила

- Каждый платеж принадлежит одному пользователю.
- Подписка активируется только после успешной оплаты.
- Неуспешные платежи не дают доступ.
- Повторная обработка одного платежа невозможна.
- История платежей не изменяется после завершения операции.
- Все внешние платежные события проходят проверку.

---

# Инварианты

- Payment всегда имеет статус.
- Payment всегда связан с пользователем.
- Subscription всегда имеет срок действия.
- Активная подписка существует только после успешной оплаты.
- Сумма платежа не может быть отрицательной.
- Один внешний платеж не может создать несколько подписок.

# Правила разработки

- Router не содержит бизнес-логики.
- Service содержит финансовую логику.
- Repository работает только с данными.
- Платежные провайдеры подключаются через адаптеры.
- Все изменения платежной логики документируются.
- Изменение событий требует обновления Event Catalog.
