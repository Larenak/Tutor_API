# Назначение

Данный документ описывает архитектуру проекта, используемый технологический стек, принципы взаимодействия компонентов и правила организации кода.

Архитектура должна обеспечивать:

- модульность;
- масштабируемость;
- расширяемость;
- простоту сопровождения;
- независимость бизнес-модулей.

Все технические решения проекта должны соответствовать данному документу.

---

# Общая архитектура

Проект реализуется как **модульный монолит (Modular Monolith)**.

Каждая бизнес-область выделяется в отдельный модуль со своей ответственностью, внутренней логикой и API.

Модули взаимодействуют между собой исключительно через публичные сервисы и доменные события.

Прямой доступ к внутренним компонентам другого модуля запрещён.

---

# Архитектурный стиль

Используются следующие архитектурные подходы:

- Modular Monolith;
- Domain Driven Design (DDD);
- Layered Architecture;
- REST API;
- Event Driven Communication (внутри приложения);
- Repository Pattern;
- Service Layer;
- Dependency Injection.

# Слои приложения

Каждый запрос проходит через несколько уровней.

```
Client

↓

API

↓

Service

↓

Repository

↓

Database
```

### API

Отвечает за:

- получение HTTP-запросов;
- валидацию данных;
- возврат ответа.

API не содержит бизнес-логики.

---

### Service

Содержит бизнес-логику.

Именно сервис принимает решения и координирует работу остальных компонентов.

---

### Repository

Отвечает исключительно за работу с базой данных.

Repository не содержит бизнес-логики.

---

### Database

Постоянное хранение данных.

---

# Взаимодействие модулей

Разрешается:

```
Module A

↓

Public Service

↓

Module B
```

или

```
Module A

↓

Domain Event

↓

Module B
```

Запрещается:

- импорт внутренних сервисов другого модуля;
- обращение к моделям другого модуля;
- изменение данных другого модуля напрямую;
- доступ к приватным компонентам модуля.

---

# Принципы разработки

При разработке необходимо соблюдать следующие правила.

## Single Responsibility

Каждый класс отвечает только за одну задачу.

---

## Dependency Inversion

Модули не должны зависеть от деталей реализации друг друга.

---

## DRY

Не допускается дублирование бизнес-логики.

---

## KISS

Предпочтение отдаётся простым решениям.

---

## YAGNI

Функциональность реализуется только при наличии реальной необходимости.

---

## Явные зависимости

Все зависимости должны быть очевидны и легко прослеживаться.

---

## Изоляция модулей

Каждый модуль является самостоятельной бизнес-единицей.

---

## Расширяемость

Новая функциональность должна добавляться без изменения существующих модулей.

---

# Масштабирование

Архитектура должна позволять:

- добавлять новые модули;
- заменять AI-провайдеров;
- подключать новые модели LLM;
- изменять способ хранения файлов;
- подключать новые платёжные системы;
- масштабировать отдельные инфраструктурные компоненты.

При необходимости модульный монолит может быть разделён на микросервисы без изменения бизнес-логики модулей.

---

# Definition of Done

Архитектура считается соответствующей требованиям проекта, если:

- все бизнес-области разделены на независимые модули;
- отсутствуют циклические зависимости;
- взаимодействие модулей осуществляется через публичные сервисы и события;
- бизнес-логика располагается только в сервисах;
- AI-подсистема изолирована от бизнес-модулей;
- проект соответствует принципам модульного монолита;
- архитектура допускает дальнейшее масштабирование без существенного рефакторинга.
